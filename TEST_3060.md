# TEST_3060.md — end-to-end smoke test on the RTX 3060 box

revv v1.0 was built and tested on a Mac with no NVIDIA GPU. Everything that does
not need CUDA has been exercised; everything that does is listed here.

**Do not run this while the box is busy.** The 3060 belongs to a measurement
chain. Check that nothing is mid-run before you start, and remember that the
certified configuration needs the card essentially empty: it peaks at 11,958 MiB
of about 12,044 usable.

---

## What was already verified on the Mac

Do not re-test these; they are done.

| Area | Evidence |
|---|---|
| GGUF header parser | Parsed 19 `ggml-vocab-*.gguf` files plus two real quantized models. `data_offset + tensor_data_bytes == file_size` held EXACTLY on both, which validates every block-size constant the files exercise. 1.5 GB file parses in 0.20 s, proving no tensor data is read. |
| MTP draft-head detection | Synthetic GGUFs covering: head present, uppercase `NEXTN`, bare `nextn.` prefix, and the critical negative control (`blk.0.nextnormal.weight` must NOT match). All correct. |
| CERTIFIED badge cannot be forged | A synthetic file renamed to `Qwen3.8-27B-UD-IQ3_XXS.gguf` still reports COMPATIBLE, because the verdict also requires the quantization to be IQ3_XXS. |
| Download resume | Local HTTP server tests: clean download, interrupt-and-resume (verified a `Range:` header was sent and fewer bytes transferred), a server that ignores `Range` and returns 200 (truncate-and-restart), size-mismatch rejection, no-op when the file already exists, and 404 failing immediately without retries. |
| Doctor with no GPU | Reports the missing `nvidia-smi` cleanly and says there is no CPU path. |
| Proxy, toggle, compare, daemon | Run end to end against a real llama-server on the Mac with a small Qwen GGUF: `up`, `status`, request forwarding, `X-Revv-Mode` header, per-request t/s telemetry, `toggle`, `compare`, `down`, and a confirmed absence of orphaned processes. |
| Orphan reaping | `revv up`, then `kill -9` the supervisor, then `revv down`: the orphaned llama-server is found and killed. This test found a real bug — `down` read the backend pid from the status endpoint, which dies with the supervisor. The pid is now persisted to `~/.revv/run/revv.json` on every start and every mode switch. |
| Failure modes | Bad tier, unknown build, missing file, junk GGUF, no server, no model: all produce a clear message plus a fix, and exit 1. |
| Flag syntax | Every flag revv emits was checked against `common/arg.cpp` at the pinned commit, and all of them are accepted by a real llama-server. |

## The two things most likely to break, and why

**RISK 1 — RESOLVED, 2026-09-02. Kept here because the check still runs.**
The concern was that revv makes two substitutions against the certified setup:
it uses the GGUF's *embedded* chat template (via `--jinja`) instead of the
external `chat_template.jinja` the certification used, and it disables thinking
*server-side* instead of per-request. Both were measured on the real 27B and
both are safe:

- Thinking is suppressed by the server-side flag alone (0 reasoning characters
  with no per-request kwarg, against a positive control that emitted 803).
- The embedded template is output-neutral: a 25-task HumanEval run produced
  **byte-identical completions on 25/25 tasks** versus the certified run under
  the external template.

**Consequence: revv does not ship a chat template file, and does not need to.**
That packaging question is closed.

Since then the launch flag has moved from the deprecated
`--chat-template-kwargs '{"enable_thinking":false}'` to `--reasoning off`
(identical mechanism upstream; revv probes `--help` and falls back automatically
on older builds). Phase 5 re-checks that the migration still suppresses thinking.

**RISK 2 — VRAM headroom.** The certified config peaks at 11,958 MiB. Anything
else on the card, including a login session, turns that into a CUDA OOM during
the first request rather than at load. `revv doctor` warns when more than 250 MiB
is already in use.

## Phase 0 — get the code on the box

## Phase 1 — install

    cd ~/revv
    sh install.sh --patched

Expected: python check passes, clones llama.cpp at
`daef7b6874397a5a7c3d7e38b55e2ee0adf7da38`, applies both patches cleanly, builds
with CUDA, links `llama-server` into `~/.revv/bin`, and writes `~/.revv/build.json`.

Check:

    cat ~/.revv/build.json
    # patches must list BOTH mmvq_iquant_decode.patch and pr26004-rebased-daef7b687.patch
    export PATH="$HOME/.revv/bin:$PATH"

The build takes a while. If a patch fails to apply, the tree is not at the pinned
commit — `git -C ~/.revv/src/llama.cpp rev-parse HEAD` will say so.

Note: the box already has a llama.cpp build. If you would rather not rebuild,
`install.sh` will detect an existing `llama-server` on PATH and skip the build —
but then `revv doctor` reports "build provenance unknown" and `revv bench` compares
against the stock reference rather than the patched one, which is correct
behaviour, not a bug.

## Phase 4 — bring the stack up

    revv up /data/projects/q27b_on_12gb/models/unsloth-q27b/Qwen3.8-27B-UD-IQ3_XXS.gguf
    revv status

Expected: mode revv, tier 12GB, speculation **on**, api on
`http://127.0.0.1:8080/v1`.

Sanity request:

    curl -s http://127.0.0.1:8080/v1/chat/completions \
      -H 'Content-Type: application/json' \
      -d '{"model":"revv","messages":[{"role":"user","content":"Write a Python function that reverses a linked list."}],"max_tokens":200,"temperature":0}' \
      | python3 -c 'import json,sys; m=json.load(sys.stdin)["choices"][0]["message"]; print("REASONING:", len(m.get("reasoning_content") or "")); print(m["content"][:300])'

**`REASONING: 0` is the pass condition for RISK 1.** Anything else means the
thinking switch is not taking effect.

While a generation is running, in another shell:

    nvidia-smi --query-gpu=memory.used --format=csv,noheader,nounits -lms 500

Expected peak around **11,958 MiB**. Materially higher means something changed;
materially lower means a flag is not being applied.

## Phase 5 — bench (the number that matters)

    revv bench

Expected:
- the **thinking check** must print `PASS`, with arm A at 0 reasoning
  characters and arm C (the positive control) above 0. This is the
  authoritative check, and it is authoritative *because* arm A sends no
  `chat_template_kwargs`: an earlier version of this file nominated `revv
  bench` before that arm existed, when every bench request sent the kwarg
  itself and therefore masked exactly the failure it claimed to detect.
  A `PASS` with arm C at 0 reads `INCONCLUSIVE`, which is not a failure but
  means the probe could not prove itself live.
- decode **36-39 t/s** under this protocol; the reference measurement is
  37.9 t/s on the patched build. Do not compare against the 34.4/36.7
  certification figures — different prompt, different harness, ~10% gap.
- spread across the 4 requests around 1%, certainly under 2%
- the verdict line should read "on target"

Failure readings:
- **~22 t/s** means speculation is not running. Check `revv status` says
  speculation on, and that `revv inspect` found the draft head.
- **under 30 t/s with speculation on** is a real regression; capture the output,
  `revv doctor`, and `~/.revv/logs/llama-server.log`.

## Phase 6 — toggle and compare (the demo)

    revv toggle          # -> STOCK
    revv status          # confirm the port did not move
    revv toggle          # -> revv
    revv compare

Expected from `compare`, and this is the screenshot:
- STOCK around **20 t/s** (the measured no-speculation figure is 20.00 t/s at
  q8_0 KV, 20.15 at f16 which is what STOCK mode uses)
- revv around **34-37 t/s**
- STOCK spending **many more tokens** than revv on the same prompt, because
  thinking is on in STOCK — the measured effect is 474 vs 158.8 tokens per
  HumanEval task
- consequently a "time to done" ratio noticeably larger than the "decode rate"
  ratio. That gap is the whole argument: raw t/s is not work speed.

Confirm a toggle takes roughly 10-15 s (weights served from page cache, not
re-read from disk). If it takes 60+ s, the page cache is being evicted and the
README's claim needs softening.

## Phase 7 — teardown, and the thing that must not happen

    revv down
    nvidia-smi          # must show NO llama-server holding VRAM
    pgrep -fl llama-server || echo "clean"

Then confirm the daemon really is detached, since that is the point of `up`:

    revv up <model>
    exit                # close the ssh session entirely
    ssh ollama 'export PATH="$HOME/.revv/bin:$PATH"; revv status && revv down'

Expected: `status` still works after the session that started it is gone, and
`down` cleans up.

Also confirm the orphan-reaping path, which is the failure that would strand
11 GB of VRAM:

    revv up <model>
    kill -9 $(python3 -c "import json;print(json.load(open('$HOME/.revv/run/revv.json'))['pid'])")
    revv down            # must find and reap the now-orphaned llama-server
    pgrep -fl llama-server || echo "clean"

## Phase 8 — the prebuilt install path (NEW, never run end to end)

This is the one path with no field evidence. `install.sh` now downloads a
prebuilt `llama-server` instead of compiling, and while the artifact has been
packaged, hash-verified and its launcher tested across every invocation shape,
**nobody has yet installed it from scratch on a machine that did not build it.**
That is what this phase is for. Run it on a box that is NOT the one that
produced the binary, or at minimum into a clean `REVV_HOME`.

Prerequisite: the release must be published. Until the founder runs the command
in `release/v1.1.0-binaries.md`, rung 1 will 404 and fall back to source — which
is itself worth confirming (step 1 below).

    # 1. before the release exists: must fail clearly and fall back, not hang
    REVV_HOME=/tmp/revv-pre1 sh install.sh --prebuilt

Expected: a clear "not published yet" style message naming the URL, then either
a fallback to the source rung or a clean exit. NOT a stack trace, NOT a silent
success, NOT a fallback to `--upstream`.

    # 2. after the release is published: the happy path
    REVV_HOME=/tmp/revv-pre2 sh install.sh
    cat /tmp/revv-pre2/build.json

Expected: downloads ~78 MB, verifies sha256
`3522ef73cb9a93b865e0cfe26c6ccb0f7021e3415fc011e844537bf948bc4423`, extracts,
symlinks `bin/llama-server`, and writes a manifest with
`"install_method": "prebuilt"` and both patch names.

    # 3. THE test: does the downloaded binary actually run?
    export REVV_HOME=/tmp/revv-pre2 PATH="/tmp/revv-pre2/bin:$PATH"
    llama-server --version
    revv doctor

Expected: `--version` prints a version banner rather than a loader error. This
is the step that would catch a broken RUNPATH or a missing CUDA runtime
library. If it fails with `error while loading shared libraries`, capture the
exact soname — that is the whole finding.

`revv doctor` must report `install: revv prebuilt binary (patched, CUDA)` and
`kernel patch applied`.

    # 4. end to end on the real model
    revv up <path-to-Qwen3.8-27B-UD-IQ3_XXS.gguf>
    revv bench
    revv down

Expected: the same numbers as Phase 5 — around 37-39 t/s, thinking check PASS.
If the prebuilt is materially slower than a source build of the same commit,
that is a real finding and worth reporting.

    # 5. idempotency: re-running must not re-download 78 MB
    sh install.sh          # should reuse the cached tarball

    # 6. the other two rungs still work
    REVV_HOME=/tmp/revv-up sh install.sh --upstream   # Vulkan; doctor should WARN it is not CUDA
    REVV_HOME=/tmp/revv-src sh install.sh --source    # the old compile path

Report for each step: pass/fail, the actual output, and for step 3 the exact
loader error if there is one.

## Phase 9 — for the WSL2 box specifically

Four things only a second, foreign machine can settle. The 3060 build box
cannot answer any of them, because it is the machine everything was built and
measured on.

**1. `revv adopt` against a real store.** Every adopt test so far ran against
fixtures we wrote ourselves. Point it at a genuine ollama or LM Studio
installation with models actually pulled through those tools:

    revv adopt

Confirm: it finds them, names them correctly, is read-only on their
directories (compare a recursive listing with mtimes before and after), and
that `revv serve <adopted-name>` then works. The interesting case is a model
whose ollama blob filename is a content hash — revv is supposed to identify it
by size and still recognise a certified file.

**2. The prebuilt install, on a machine that did not build it.** This is the
single largest untested surface. Requires the release to be published first.

    REVV_HOME=/tmp/revv-fresh sh install.sh
    export REVV_HOME=/tmp/revv-fresh PATH="/tmp/revv-fresh/bin:$PATH"
    llama-server --version        # the step that catches a broken RUNPATH
    revv doctor                   # must report: install: revv prebuilt binary

If it fails with `error while loading shared libraries`, capture the exact
soname — that is the finding. Note this box is WSL2 on glibc that may be below
2.38; if so, the prebuilt should REFUSE and fall back to source, which is
itself the correct result and worth confirming.

**3. Confirm the compare/bench fix.** That box previously had `revv compare`
reading 29.7 t/s where `revv bench` read 34.31 — a 14% disagreement between two
of our own instruments. compare now requests `timings_per_token` so it uses
llama-server's own decode rate rather than a client-side wall-clock fallback.

    revv bench && revv compare

Expected: the two now agree. If a transport note appears saying the client
observed materially fewer tokens/second than the server reported, that
CONFIRMS the diagnosis (proxy/SSE/loopback cost on that host) — capture it
either way. This is the one open question from the last field report.

**4. The speed tier, end to end.** Never run anywhere outside the build box.

    revv get speed          # 16.0 GiB, from the MTP repo
    revv inspect ~/.revv/models/Qwen3.6-35B-A3B-UD-Q3_K_XL.gguf
    revv up ~/.revv/models/Qwen3.6-35B-A3B-UD-Q3_K_XL.gguf
    revv bench

Check, in order:
- `inspect` reports **CERTIFIED (speed line)** and an MTP draft head at
  `blk.40.nextn.*`. If the head is ABSENT, the wrong repo was downloaded —
  there is a same-named file in `unsloth/Qwen3.6-35B-A3B-GGUF` without it.
- `serve` prints `16 expert layers on CPU` among its levers and the host-RAM
  line. On a 16 GiB machine, watch whether the host-RAM warning fires.
- `bench` should land near **55.9 t/s** with acceptance well above zero. Around
  35 t/s with acceptance 0 means speculation is not running. (48.5 t/s was the
  pre-2026-09-05 speed-tier figure, before the `-t` heuristic and the
  n-gram+MTP drafter stack were certified; see BENCHMARKS.md section 18.
  Landing at ~48.5 now means one of those two levers is not engaging.)
- Watch host RSS during generation (`ps -o rss= -p <backend_pid>`); expect
  roughly 7.2 GiB. Materially more on a 16 GiB box is the interesting failure.

Also worth one run: the certified config now ships `-ctxcp 0`. Confirm the
server survives more than one request, which is the whole point of that flag.

For each phase: pass/fail plus the actual output. Specifically capture:

1. `revv doctor` output in full.

3. `revv bench` output in full, including whether the thinking canary fired.

**53-58 t/s** on the speed tier), or the thinking canary fires, stop and report
before anything is published — those are the two results that would change what
the README is allowed to say.

The flagship window here is the *bench* protocol's, matching the 37.9 t/s
reference quoted in Phase 5 above. An earlier revision of this file said
"34-37 t/s", which was the *certification* protocol's window (34.4/36.7) and
does not apply to `revv bench` — it made the reference box's own correct
37.86 t/s read as out-of-window. Do not reintroduce it.
