## What is in the artifact

**Provenance.** llama.cpp at pinned upstream commit
`daef7b6874397a5a7c3d7e38b55e2ee0adf7da38` (build b10712) with revv's patches:

- `mmvq_iquant_decode.patch` — CUDA sub-4-bit i-quant decode (`mmvq.cu`,
  `vecdotq.cuh`). +10.1% raw decode, +2.5% on the shipping speculative config,
  output-neutral (3/3 prompts byte-identical against stock at the same commit).
- `pr26004-rebased-daef7b687.patch` — upstream PR #26004 rebased onto that
  commit (`server-context.cpp`), making slot save/restore work on this hybrid
  recurrent architecture. First request after restore: 149 ms vs 15,366 ms.

**Target architectures.** Compiled for `sm_75 sm_80 sm_86 sm_89 sm_90` —
Turing, Ampere (datacenter and consumer), Ada Lovelace, Hopper.
**sm_120 (RTX 50-series / Blackwell) is excluded**: the build toolchain
(nvcc 12.0) cannot target it. Those cards should use `--upstream` or
`--source`. `install.sh`'s `check_prebuilt_arch` now does a membership test
against this list and names the set in its mismatch message.

**Bundled CUDA runtime.** The archive ships its own runtime libraries, so the
user needs only an NVIDIA driver providing `libcuda.so.1`:

    libcudart    12.0.146
    libcublas    12.0.2.224
    libcublasLt  12.0.2.224

**Tarball layout:**

    llama-server          launcher script (sets LD_LIBRARY_PATH to lib/)
    llama-server.bin      the real ELF
    llama-bench           launcher script
    llama-bench.bin       the real ELF
    lib/*.so*             bundled CUDA runtime + llama.cpp shared objects
    PROVENANCE.txt        full build recipe and per-file hashes
    SHA256SUMS            per-file checksums for `sha256sum -c`

A launcher is needed because the binaries carry an absolute RUNPATH into the
build machine's tree and would otherwise not find their own libraries.

## Verification done before staging

- `sha256sum -c` on the tarball passes; the value matches the one now pinned
  in `install.sh`.
- `ldd` on `llama-server.bin` reports **zero** missing shared libraries.
- The launcher resolves correctly when invoked through a symlink from another
  directory — the layout `install.sh` actually creates. It was tested across
  all six invocation shapes under both `sh` and `dash`: absolute path,
  relative path from another directory, symlink from a different directory, a
  symlink chain, an inherited `LD_LIBRARY_PATH` (prepended, not clobbered),
  and a missing binary (clear error, exit 1). The first cut of the launcher
  was broken in exactly the symlink case that matters and was caught by that
  test.
- glibc / GLIBCXX floors were read out of the ELF symbol versions rather than
  assumed: glibc 2.38, GLIBCXX_3.4.32.
- **Live run on the build host:** `llama-server` started with the certified
  35B shipping argv, answered `/health`, and returned a completion. VRAM peak
  11,662 MiB.

Speed was measured on the prior sm_86-only build (37.86 t/s at 11,830 MiB
peak, 0.8% spread, `revv bench` protocol, RTX 3060 12GB). The CUDA kernel
source is unchanged in this multi-arch rebuild — only the target architecture
list grew — so that figure should still hold on sm_86.

**Remaining gap:** it has not been installed from scratch on a machine other
than the one that built it. That is what the "this path is new" section of the
release notes tells users, and why a failure report from a fresh box is
genuinely useful.
