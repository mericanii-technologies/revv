## Release notes (copy into `RELEASE_NOTES.md`)

    A prebuilt, patched `llama-server` for Linux x86_64 with CUDA, so you do not
    have to build llama.cpp yourself.

    ## Why this exists

    Upstream llama.cpp publishes prebuilt CUDA binaries for Windows only. For
    Linux it ships CPU, Vulkan, ROCm and SYCL builds — no CUDA. So on Linux
    there has never been an official "download and run" path for an NVIDIA card,
    and the first thing a new user hits is the CUDA build gauntlet: cmake, then
    the toolkit, then a host compiler nvcc accepts, then a glibc that toolkit
    accepts. One reported setup lost about half an hour to exactly that.

    This asset removes that step.

    ## What it is

    llama.cpp at pinned upstream commit `daef7b6874397a5a7c3d7e38b55e2ee0adf7da38`
    (build b10712) with revv's two patches applied:

    - `mmvq_iquant_decode.patch` — CUDA sub-4-bit i-quant decode. +10.1% raw
      decode, +2.5% on the shipping speculative config. Verified output-neutral:
      3/3 prompts byte-identical against a stock build of the same commit.
    - `pr26004-rebased-daef7b687.patch` — upstream PR #26004 rebased onto that
      commit, making llama-server's slot save/restore work on this hybrid
      recurrent architecture. First request after restore: 149 ms vs 15,366 ms.

    Measured on an RTX 3060 12GB with the `revv bench` protocol: **37.86 t/s**
    at 11,830 MiB peak, 0.8% spread.

    ## Requirements — read these

    - **glibc 2.38 or newer.** Ubuntu 24.04+ or Debian 13+. Ubuntu 22.04 will
      NOT work; build from source there.
    - **libstdc++ with GLIBCXX_3.4.32** (GCC 13+ runtime).
    - **CUDA runtime libraries**, which are NOT bundled: `libcudart.so.12`,
      `libcublas.so.12`, `libcublasLt.so.12`. These come from the CUDA
      *runtime*, not the full toolkit — no nvcc, no headers, no compiler.
    - **Compiled for sm_86 only** (Ampere; 30-series). Other architectures rely
      on driver JIT from PTX and may fail. If you are not on Ampere, build from
      source.

    ## Trust

    This is a **fork build**, not an official llama.cpp release. It was built and
    signed off by Mericanii. If you would rather not run a third-party binary,
    revv supports two other paths and will not push you toward this one:

        ./install.sh --upstream   # official llama.cpp prebuilt (CPU or Vulkan)
        ./install.sh --source     # build from source, with toolchain preflights

    Verify what you downloaded:

        sha256sum -c revv-llama-server-1.1.0-linux-x86_64-cuda12.tar.gz.sha256
        tar xzf revv-llama-server-1.1.0-linux-x86_64-cuda12.tar.gz
        cd revv-llama-server-1.1.0-linux-x86_64-cuda12
        sha256sum -c SHA256SUMS

    The bundle ships `PROVENANCE.txt` with the full build recipe and the
    per-file hashes.

    ## This path is new

    It has been packaged and verified for structure and provenance, but it has
    not yet been installed from scratch on a machine other than the one that
    built it. If it fails on yours, that report is genuinely useful — open an
    issue with `revv doctor` output.

## Two decisions left to you

1. **Bundling the CUDA runtime.** Right now `libcudart`/`libcublas`/`libcublasLt`
   come from the user's system, so they still need the CUDA runtime installed
   (much smaller than the toolkit, but not nothing). We could bundle them and
   make the tarball fully self-contained — llama.cpp does exactly this for its
   Windows CUDA zips. It would add roughly 600 MB and it is a redistribution
   question, so it is your call, not mine. Not done.

2. **sm_86 only.** The build targets the 3060's architecture. A multi-arch build
   (`86;89;90`) would cover more cards at the cost of build time and size. Worth
   doing before this is promoted widely.

## Verification done before staging

- sha256 of `llama-server`, `libllama-server-impl.so` and `libggml-cuda.so.0.22.0`
  match `v11_candidate.md` exactly — the artifact is the measured build.
- Symlink structure restored after copy (scp dereferences them), which took the
  bundle from 630 MB to 216 MB, 78 MB compressed.
- glibc/GLIBCXX floors read out of the ELF symbol versions rather than assumed.
- A launcher script is included because the binaries carry an absolute RUNPATH
  into the build machine's tree and would otherwise not find their own
  libraries. The launcher sets `LD_LIBRARY_PATH` to the bundled `lib/`.

- The launcher was tested across all six invocation shapes under both `sh` and
  `dash`: absolute path, relative path from another directory, **symlink from a
  different directory** (the layout `install.sh` actually creates), a symlink
  chain, an inherited `LD_LIBRARY_PATH` (prepended, not clobbered), and a
  missing binary (clear error, exit 1). The first cut of the launcher was
  broken in exactly the symlink case that matters and was caught by that test.

**Not yet verified:** that the extracted bundle actually *runs* on a clean
Linux machine — the ELF cannot be executed from the packaging host, and the box
that could confirm it was mid-measurement. That is the one gap, and it is why
the notes say the path is new.
